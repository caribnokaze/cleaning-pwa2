# モバイル本番統合 API 仕様（初回リリース案）

## 目的と適用範囲

iOS・Android のネイティブ写真ピッカーから、既存の TOCORO 清掃写真管理へ
安全に写真を送信するための API 契約を定義します。初回リリースでは Web 版と
同じ全員共通パスワードを使います。

この文書は設計のみを扱います。本番 URL、秘密値、AWS アクセスキーはコードや
アプリへ保存しません。既存の本番環境へこの文書だけで変更は加えません。

## 設計原則

- パスワードは利用者が入力し、アプリへ永続保存しない
- AWS 認証情報をアプリへ配布しない
- API が短時間有効な S3 署名付き URL を発行する
- 写真はアプリから S3 へ直接送信する
- 認証トークンは 72 時間で失効する
- 署名付き URL は 5 分で失効する
- 認証トークン、署名付き URL、パスワードをログへ出力しない
- 既存の S3 キー形式 `date/site/staff/photoId/filename` を維持する
- 1回の要求と中断復帰単位は最大100枚とする
- 既存システムとの互換性を保つため、`photoId` は写真カテゴリーIDとして扱う

## 写真カテゴリー

既存Web版では `photoId` が写真ごとの一意なIDではなく、写真カテゴリーを表します。
初回リリースの操作方式は「カテゴリーを選択 → 写真を最大100枚選択」とします。
利用者は先にカテゴリーを1つ選び、そのカテゴリーに属する写真を独自高速ピッカーで
選択します。複数カテゴリーを送る場合は選択操作をカテゴリーごとに繰り返します。
写真選択画面の上部には選択中のカテゴリー名を表示し、確定前に取り違えを確認できる
ようにします。

初回リリースで画面に表示するカテゴリーIDは、現行Web版で実際に使っている次の
項目に限定します。

- `photos_amenity`
- `photos_general`
- `regular_1`〜`regular_8`
- `photos_filter`

`photos_kitchen`、`photos_bath`、`photos_living`、`photos_bedroom`、
`photos_hallway`、`photos_equipment`、`photos_others` は既存コードに残る旧項目で、
初回リリースの画面には表示しません。再利用する場合はWeb版との運用確認後に別途
有効化します。許可リストはサーバー側で管理し、アプリから任意のIDを追加することは
できません。

## 正式版モバイルUI

現在のプロトタイプ画面は、写真選択・圧縮・送信性能を検証するためのものです。
正式版では検証用ボタンや所要時間表示を除き、現行Web版に近い次の流れにします。

1. 共通パスワードでログインする
2. 清掃日、担当者、現場を選択する
3. 作業区分を選択する
4. 表示されたカテゴリーごとに写真を選択する
5. 入力内容と枚数を確認して送信する
6. 送信状況と結果を確認する

### 報告情報画面

- 清掃日は日付選択とし、初期値は当日とする
- 担当者と現場は現行Web版と同じ候補を検索して選択する
- 作業区分は「通常清掃」「定期清掃＋フィルター清掃」「定期清掃のみ」
  「フィルター清掃のみ」から選択する
- 戻って修正しても、選択済み写真と送信前の入力状態を保持する

### カテゴリー写真画面

通常清掃の2項目は、すべての作業区分で表示します。

| 区分 | カテゴリー | ID | 必須枚数 | 最大枚数 |
|---|---|---|---:|---:|
| 通常 | タオル・歯ブラシ・Wi-Fi・NetFlix | `photos_amenity` | 1 | 10 |
| 通常 | その他全般 | `photos_general` | 30 | 100 |
| 定期 | 定期清掃1〜7 | `regular_1`〜`regular_7` | 各1 | 各10 |
| 定期 | 定期清掃8 | `regular_8` | 0 | 10 |
| フィルター | フィルター清掃 | `photos_filter` | 1 | 10 |

- 定期清掃を含む作業区分では、通常項目に加えて定期清掃1〜8を表示する
- フィルター清掃を含む作業区分では、通常項目に加えてフィルター清掃と
  作業時間を表示する
- フィルター作業時間は15分から120分まで15分刻みで選択必須とする
- 各行にはカテゴリー名、必須表示、現在枚数と最大枚数、選択・変更ボタンを表示する
- 行を押すと、そのカテゴリー名と最大枚数を渡して独自高速ピッカーを開く
- ピッカー上部にカテゴリー名と選択枚数を常時表示する
- 必須枚数を満たした行には完了表示を付ける
- 作業区分を変更して不要になったカテゴリーの写真は、確認なしに破棄しない

### 確認・送信画面

- 清掃日、担当者、現場、作業区分、フィルター作業時間を表示する
- カテゴリー別の選択枚数と合計枚数を表示する
- 必須項目を満たすまでは送信ボタンを有効にしない
- 送信開始後は全体件数、成功、未完了、失敗を表示する
- 通信断やアプリ終了後は「未完了の送信があります」を表示し、未完了分だけ再開する
- 同じ写真を二重送信しない

正式版には「比較用ピッカー」「通信失敗テスト」「検証S3から削除」などの
検証専用操作や、準備・送信時間の開発者向け計測表示を含めません。

## 認証

### `POST /api/mobile/login`

要求:

```json
{
  "password": "利用者が入力した共通パスワード"
}
```

成功（200）:

```json
{
  "token": "期限付き署名トークン",
  "expiresAt": 1788400000
}
```

失敗:

- `400`: 入力形式が不正
- `401`: パスワードが不一致
- `429`: 10分間に5回の失敗
- `500`: 認証サービス内部エラー

以後のモバイル API は `Authorization: Bearer <token>` を要求します。トークンは
iOS Keychain または Android Keystore で保護し、平文のアプリストレージには
保存しません。ログアウト時は端末側から削除します。

## 署名付きアップロード URL

### `POST /api/mobile/photos/presigned-urls`

要求:

```json
{
  "uploadId": "端末で生成した一意なID",
  "date": "2026-09-03",
  "site": "現場名",
  "staff": "担当者名",
  "photoId": "photos_general",
  "files": [
    {
      "clientPhotoId": "端末内で一意なID",
      "contentType": "image/jpeg",
      "size": 72341
    }
  ]
}
```

成功（200）:

```json
{
  "uploadId": "端末で生成した一意なID",
  "expiresAt": 1788357100,
  "files": [
    {
      "clientPhotoId": "端末内で一意なID",
      "filename": "mobile_upload-id_001.jpg",
      "key": "2026-09-03/現場名/担当者名/photos_general/mobile_upload-id_001.jpg",
      "uploadUrl": "S3署名付きURL"
    }
  ]
}
```

検証規則:

- `date` は `YYYY-MM-DD`
- `site` と `staff` は1〜100文字で、`/`、`\\`、NULL文字を禁止
- `photoId` はサーバー側のカテゴリー許可リストと一致すること
- ファイルは1〜100件
- `contentType` は `image/jpeg` のみ
- 1ファイルおよび要求全体の上限サイズをサーバー側で検証
- S3 キーは検証済みのカテゴリーIDとファイル情報からサーバーが決定する
- ファイル名はサーバーが `uploadId` と連番から決定し、既存写真を上書きしない
- `photos_filter` では別途検証した作業時間をファイル名へ付加する

## 送信完了の確定

### `POST /api/mobile/photos/confirm`

要求:

```json
{
  "uploadId": "一意なID",
  "photos": [
    {
      "clientPhotoId": "端末内で一意なID"
    }
  ]
}
```

サーバーは S3 オブジェクトの存在、Content-Type、サイズを確認し、確認できた写真
だけを既存の一覧・ギャラリーへ公開します。同じ `uploadId` と `clientPhotoId` の
再送は同じ保存先と結果を返し、重複写真を作らない冪等な処理にします。
S3キーはクライアントから再送させず、署名付きURL発行時にサーバーが記録した対応を
参照します。この対応記録には有効期限を設け、完了後または期限後に削除します。

成功（200）:

```json
{
  "uploadId": "一意なID",
  "confirmed": ["client-photo-id-1"],
  "missing": []
}
```

## 中断復帰

### `GET /api/mobile/uploads/:uploadId`

指定した送信について、S3保存済み・確認済み・未完了の写真IDを返します。アプリは
未完了だけの署名付きURLを再取得して再送します。

端末に永続保存してよい項目:

- `uploadId`
- 撮影日、現場名、担当者名
- 写真カテゴリーID
- iOS PhotoKit ID または Android MediaStore URI
- `clientPhotoId`、ファイル名、処理状態、再試行回数

永続保存しない項目:

- 共通パスワード
- 認証トークン（OSの安全な資格情報領域以外）
- 署名付きURL
- 圧縮画像の Base64 表現

トークン失効時は再ログインを求め、同じ `uploadId` から未完了分だけ再開します。

## エラーと再試行

- `401`: 再ログインし、状態照合後に再開
- `403`: 期限切れ署名URLを再取得
- `409`: サーバー状態を再照合
- `429`: `Retry-After` に従う
- `5xx`・通信断: 指数バックオフにランダムな揺らぎを加えて再試行
- 画像取得・圧縮失敗: その写真だけ失敗として残し、他の写真を継続

自動再試行には上限を設け、上限後は利用者が「未完了の送信を再開」を選べるように
します。

## セキュリティ要件

- HTTPS のみ
- 本番と検証の API URL・S3 prefix・秘密値を完全に分離
- 共通パスワードと署名秘密値は Secrets Manager で管理
- Lambda / AppRunner 実行ロールは必要な S3 操作だけを許可
- CORS は正式なWebオリジンと必要なメソッド・ヘッダーだけを許可
- ログは `uploadId`、件数、所要時間、結果コードに限定
- レート制限は複数インスタンスで共有できる保存先を使用
- S3暗号化、Block Public Access、アクセスログを有効化
- アプリには検証用削除ボタン、通信失敗スイッチ、秘密値入力済み初期値を含めない

## 本番へ触れない実装・検証順

1. この仕様をレビューし、API名とレスポンス形式を確定する
2. 検証専用APIに本番用予定のパスを追加して自動テストする
3. モバイルアプリをビルド環境別URLへ対応させる
4. 新しい非本番S3 prefixでWebギャラリー互換性を確認する
5. iOS・Androidで2枚、100枚、中断復帰、期限切れを再試験する
6. セキュリティレビューとロールバック手順を確認する
7. 明示的な承認後にのみ、本番APIへ同じ契約を追加する

## 認証・環境切替の移行計画

検証版から正式版への切替は、一度に本番へ接続せず、次の段階に分けます。

### 段階1：検証環境で本番契約を再現

- 検証APIに `/api/mobile/login`、`/api/mobile/photos/presigned-urls`、
  `/api/mobile/photos/confirm`、`/api/mobile/uploads/:uploadId` を用意する
- アプリの画面や送信状態管理は変えず、APIの呼び出し先だけをアダプターへ分離する
- API URLはビルド時の環境変数から注入し、ソースへ本番URLを直書きしない
- 検証ビルドでは画面上に「検証環境」を常時表示する

### 段階2：ログインを送信画面から分離

- アプリ起動時にログイン画面を表示し、共通パスワードを一度だけ入力する
- パスワードはログイン要求にだけ使用し、成功・失敗にかかわらず永続保存しない
- 成功後はパスワード入力値をメモリから消去する
- 失敗回数や残り試行回数をアプリ独自に推測せず、APIの `429` と
  `Retry-After` に従う

### 段階3：認証トークンをOS安全領域へ保存

- iOSはKeychain、AndroidはKeystoreで保護される資格情報ストレージを使用する
- AsyncStorageにはトークン、パスワード、署名付きURLを保存しない
- アプリ起動時にトークンを読み、期限内なら報告入力画面へ進む
- `401`を受けた場合はトークンを削除して再ログインを求める
- 再ログイン後もAsyncStorage内の`uploadId`と写真状態を使い、未完了分だけ再開する
- ログアウト時はトークンだけを削除し、未完了送信の破棄は利用者へ確認する

### 段階4：環境別ビルドを固定

| ビルド | API接続先 | 検証用削除・計測表示 | 配布対象 |
|---|---|---|---|
| development | ローカルまたは検証API | 有効 | 開発端末のみ |
| preview | 検証API | 有効 | 実機検証担当者 |
| production | 承認済み本番API | 無効 | 正式利用者 |

- ビルド種別とAPI URLの不一致は起動時に検出して送信を禁止する
- productionビルドでは検証S3削除API、失敗注入、性能計測UIをコード経路から除外する
- previewからproductionへの切替は、設定値の変更だけでは実行せず、別ビルドとする

### 段階5：本番接続前の判定

次の全項目を満たし、明示的な承認があるまで本番API URLを設定しません。

- iOS・Androidでログイン、期限切れ、ログアウトを確認
- 5回連続失敗時の制限と解除を検証環境で確認
- 認証期限切れ後の中断復帰で重複がないことを確認
- アプリストレージ、端末ログ、Git差分に秘密値がないことを確認
- 検証用機能がproductionビルドに含まれないことを確認
- 本番追加前のバックアップ、監視、ロールバック担当と手順を確認

### ロールバック方針

- モバイル向け本番APIは既存Web APIと独立したパスで追加する
- 問題発生時はモバイルAPIだけを無効化し、既存Web版の運用を継続する
- アプリ側は送信を停止して未完了状態を保持し、写真を自動破棄しない
- 署名秘密値や共通パスワードの変更時は旧トークンを失効させ、再ログインを求める
- S3へ保存済みで未確定の写真は、保持期限後にライフサイクルで削除する

## 初回リリースの受入基準

- 共通パスワードでログインでき、5回失敗時に制限される
- 認証期限切れ後、再ログインで同じ送信を再開できる
- iOS・Androidとも100枚を重複なく保存できる
- 撮影日・現場名・担当者名・写真の向きがWebギャラリーで正しい
- 通信断・アプリ終了後は未完了分だけを送信する
- アプリ、Git、ログに秘密値や署名付きURLが残らない
- 検証ビルドに本番URL、本番ビルドに検証用操作が混入しない
